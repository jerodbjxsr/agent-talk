# CLI adapter feasibility matrix — generalizing the Frenemy relay

**Researched:** 2026-07-24.
**Versions checked:** Claude Code **2.1.219** [seen: local `claude --version` + `--help`], Codex CLI **0.144.1** [seen: local `codex --version` + `codex exec --help`], OpenCode **1.16.2** [seen: local `opencode --version` + `run --help`]. Gemini CLI, Qwen Code, and Kimi Code CLI are **not installed locally**; facts for those come from their current official docs as of today — exact version numbers for them are **UNVERIFIED**.
**Method:** primary sources only (official docs sites, vendor GitHub repos/issues, vendor help centers) plus local `--help` output for installed binaries. Anything that could not be pinned to a primary source is marked **UNVERIFIED**. Secondary sources (DeepWiki, blogs) were used only as leads and are never the sole citation for a claim.

Context: the relay pattern (see `../../ask-claude-mcp.mjs` and `../../README.md`) needs, per CLI: headless one-shot invocation, prompt via **stdin** (not argv — process-list hygiene), machine-parseable output, **subscription/OAuth auth (API-key-only disqualifies)**, enforced read-only mode, stdio MCP client support (for the reverse direction), settings isolation from a cloned repo's project config, and sane exit/timeout behavior.

## Claude Code (callee side today) — flags re-confirmed at v2.1.219

All flags the repo relies on exist in the current release, confirmed in local `claude --help` (2.1.219) **and** current docs:

- `-p, --print` — "Print response and exit"; `--output-format` `text|json|stream-json` (print mode only). [seen: local `--help`] [source](https://code.claude.com/docs/en/cli-reference)
- `--safe-mode` — "Start with all customizations disabled": CLAUDE.md, skills, plugins, hooks, MCP servers, custom commands/agents, output styles, workflows, auto-memory all skipped; auth/model/built-in tools/permissions work normally. Docs note min-version 2.1.169. [source](https://code.claude.com/docs/en/cli-reference)
- `--disallowedTools` — a bare tool name "removes the matching tools from Claude's context" (enforced removal, not advisory). [source](https://code.claude.com/docs/en/cli-reference)
- `--setting-sources` — "Comma-separated list of setting sources to load (`user`, `project`, `local`)". [source](https://code.claude.com/docs/en/cli-reference)
- `--strict-mcp-config` — "Only use MCP servers from `--mcp-config`, ignoring all other MCP configurations". [source](https://code.claude.com/docs/en/cli-reference)
- `--permission-mode` — accepts `default`, `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions` (+ `manual` alias ≥2.1.200). `acceptEdits` documented as writing files without prompting and auto-approving common fs commands (`mkdir`, `touch`, `mv`, `cp`); other shell/network still needs allow rules "otherwise the run aborts when one is attempted". [source](https://code.claude.com/docs/en/headless)
- Stdin: piping works (`cat file | claude -p "…"`); **piped stdin capped at 10 MB since v2.1.128** (exceeding → error + non-zero exit). [source](https://code.claude.com/docs/en/headless)
- JSON schema: single document with `result` (answer text), `is_error`, `session_id`, `total_cost_usd` — matches what `ask-claude-mcp.mjs` parses. [source](https://code.claude.com/docs/en/headless)
- Exit behavior: SIGTERM → aborts turn, runs SessionEnd hooks, exits **143**. Background bash killed ~5 s after the final result; background subagent wait capped at 10 min by default (≥2.1.182, `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`). [source](https://code.claude.com/docs/en/headless)

**⚠️ Forward-compat risk — `--bare`:** docs now say "`--bare` is the recommended mode for scripted and SDK calls, **and will become the default for `-p` in a future release**." Bare mode **"skips OAuth and keychain reads"** — auth must come from `ANTHROPIC_API_KEY` or an `apiKeyHelper`. If/when that default flips, a plain `claude -p` may stop using subscription auth. The relay's use of explicit `--safe-mode`/`--setting-sources` doesn't opt out of this; watch release notes and expect to need an explicit "not bare" flag. [source](https://code.claude.com/docs/en/headless)

## Codex CLI (caller side today) — re-confirmed at v0.144.1

- `codex exec [PROMPT]` — "Run Codex non-interactively." Prompt from stdin when omitted or when `-` is passed; if both stdin and argv given, stdin is appended as a `<stdin>` block. [seen: local `codex exec --help`]
- `--sandbox` values: `read-only`, `workspace-write`, `danger-full-access` — "sandbox policy to use when executing model-generated shell commands" (OS-level: Seatbelt/Landlock; enforcement is real, but note issue below). [seen: local `--help`] [source](https://learn.chatgpt.com/docs/developer-commands?surface=cli)
- Structured output: `--json` = "newline-delimited JSON events"; `-o/--output-last-message FILE` writes the final assistant message; `--output-schema` for schema-validated output. Exit-code documentation is thin ("exits non-zero if the task submission fails"). [source](https://learn.chatgpt.com/docs/developer-commands?surface=cli)
- MCP config (`~/.codex/config.toml`): `[mcp_servers.NAME]` with `command`, `args`, `env`, `startup_timeout_sec` (default 10), `tool_timeout_sec` (**default 60** — hence Frenemy's `tool_timeout_sec = 600`), `enabled`, `enabled_tools`/`disabled_tools`. Approval: `default_tools_approval_mode` or per-tool `tools.<tool>.approval_mode` with values `auto`, `prompt`, `writes`, `approve`. Project-scoped `.codex/config.toml` loads for **trusted projects only**. [source](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)
- **Headless per-tool approval requirement confirmed by independent evidence:** open issue [openai/codex#24135](https://github.com/openai/codex/issues/24135) — "codex exec: no way to allow MCP tool calls non-interactively without --dangerously-bypass-approvals-and-sandbox"; the reporter found global `approval_policy = "never"` and `default_tools_approval_mode` did **not** prevent auto-cancel ("the tool call is auto-cancelled — presumably because stdin is closed so the approval prompt's reader gets EOF"). The per-tool `approval_mode = "approve"` path this repo documents (tested at v0.144.1 per `README.md`) remains the working fix; the issue shows the *global* knobs are still broken, matching the repo's "critical config line" warning.
- Caveat: [openai/codex#20289](https://github.com/openai/codex/issues/20289) — `approval_mode = "approve"` can **still prompt** "when encrypted tool payload cannot be inspected." Low probability for a plain local stdio server, but it is a known hole in "approve means never prompt."

## Google Gemini CLI

Docs root: <https://google-gemini.github.io/gemini-cli/> (repo: google-gemini/gemini-cli). Not installed locally; **version checked: current docs site only — UNVERIFIED against a pinned release**.

**1. Headless invocation.** `gemini --prompt "..."` / `-p`, or **stdin piping**: `echo "Explain this code" | gemini`, and combined `cat README.md | gemini -p "Summarize"`. Stdin support means the prompt can stay out of argv — same hygiene as the Claude adapter. [source](https://google-gemini.github.io/gemini-cli/docs/cli/headless.html)

**2. Structured output.** `--output-format json`: answer in the `response` field (string); `stats` block (models/tools/files); `error` object "present only when an error occurred" with `type` (e.g. `ApiError`, `AuthError`), `message`, optional `code`. Single buffered document — closest schema to Claude's of any candidate. [source](https://google-gemini.github.io/gemini-cli/docs/cli/headless.html)

**3. Auth.** OAuth Google-account login, credentials cached locally; also used by Google AI Pro/Ultra subscribers. Headless: "Non-interactive mode / headless environments will use your existing authentication method, if an existing authentication credential is cached" — i.e., the Frenemy pattern (log in interactively once, then headless reuse) works; with no cached cred and no env vars it "will exit with an error in non-interactive mode." Quotas: free personal OAuth = **1000 model requests/day, 60/min**; AI Pro/Ultra = 1500/day (standard) or 2000/day, 120/min. No API key required. [source: auth](https://google-gemini.github.io/gemini-cli/docs/get-started/authentication.html) [source: quotas](https://google-gemini.github.io/gemini-cli/docs/quota-and-pricing.html)

**4. Read-only enforcement.** Layers, none of which is a single `--safe-mode` equivalent:
- `--approval-mode` = `default` | `auto_edit` | `yolo` (`--yolo`/`-y` auto-approves everything). In non-interactive runs under `default`, tools that would require confirmation cannot be approved; GitHub issues document the CLI erroring/denying such calls ("denied by policy", tools requiring approval excluded from the registry unless `--allowed-tools`): [#16012](https://github.com/google-gemini/gemini-cli/issues/16012), [#20469](https://github.com/google-gemini/gemini-cli/issues/20469). Net effect: headless default mode fails closed for edit/shell — **but that behavior is documented via issue tracker, not the docs site; treat the exact mechanism as UNVERIFIED**.
- Settings: `tools.core` (allowlist of built-in tools), `tools.exclude` (removed from discovery), `tools.allowed` (skip confirmation); CLI `--allowed-tools`. Tool-level, i.e. real enforcement. [source](https://google-gemini.github.io/gemini-cli/docs/get-started/configuration.html)
- `--sandbox`/`-s` runs tools in Docker/Podman (or Seatbelt) — heavier than needed for the relay. [source](https://google-gemini.github.io/gemini-cli/docs/get-started/configuration.html)

**5. MCP client.** `mcpServers` in `~/.gemini/settings.json` (user) or `.gemini/settings.json` (project). Stdio fields: `command`, `args`, `env`, `cwd`, `timeout` (**default 600,000 ms — 10 min, conveniently matching the relay's cap**), `trust` (bool — "bypasses all tool call confirmations for this server"), `includeTools`/`excludeTools` (exclude wins). Headless gotcha: untrusted MCP tools need confirmation, so a headless Gemini calling a relay-style server would need `trust: true` (server-wide — coarser than Codex's per-tool `approval_mode`) or `tools.allowed` entries. **Headless MCP auto-deny behavior not explicitly documented — UNVERIFIED.** [source](https://google-gemini.github.io/gemini-cli/docs/tools/mcp-server.html)

**6. Settings isolation.** Weak by default: project `.gemini/settings.json` always loads; **no `--setting-sources` analog documented**. The opt-in folder-trust feature (`security.folderTrust.enabled` in user settings) makes untrusted folders skip project settings.json and `.env`, and forces prompts for every tool — but its non-interactive behavior is **not documented (UNVERIFIED)**. `-e none` disables all extensions. [source: config](https://google-gemini.github.io/gemini-cli/docs/get-started/configuration.html) [source: trusted folders](https://google-gemini.github.io/gemini-cli/docs/cli/trusted-folders.html)

**7. Timeout/exit.** Exit codes undocumented. Known non-interactive rough edges: [#13561](https://github.com/google-gemini/gemini-cli/issues/13561) (non-interactive mode asking questions instead of doing the task), plus the policy-engine issues above. An adapter should keep Frenemy's external SIGKILL timeout.

**Verdict: viable with caveats.** Auth model is the best fit after Claude/Codex (free OAuth, cached-cred headless). Caveats: (a) settings isolation requires the opt-in folder-trust feature or accepting project-settings injection risk; (b) MCP approval is per-server `trust`, not per-tool; (c) non-interactive policy behavior has open bugs; (d) headless read-only rests on "confirmable tools fail closed" + `tools.exclude`, verified partly from issues rather than docs.

## Qwen Code

Docs: <https://qwenlm.github.io/qwen-code-docs/> (repo: QwenLM/qwen-code; "originally based on Google Gemini CLI v0.8.2", independent since v0.1; Node 22+). Not installed locally; **version checked: current docs only — UNVERIFIED against a pinned release**. [source](https://github.com/QwenLM/qwen-code)

**1/2. Headless + output (technically the best of the Gemini family).** `qwen -p "..."` or stdin pipe (`echo … | qwen`). `--output-format`: `text`, `json` ("buffered structured output as a JSON array of message objects" — `system`, `assistant`, `result`; "all messages are buffered and output together when the session completes"), `stream-json`. Documented exit codes: **55** budget exceeded, **53** session-turn cap, **130** SIGINT — plus headless budget flags `--max-wall-time`, `--max-tool-calls`, `--max-session-turns`. [source](https://qwenlm.github.io/qwen-code-docs/en/users/features/headless/)

**3. Auth — the disqualifier.** Per the official auth docs: **"Qwen OAuth (Discontinued)"** — the free tier "discontinued on 2026-04-15." Remaining options: **Alibaba Cloud Coding Plan** (a subscription, but consumed via a dedicated endpoint **API key**, format `sk-sp-…`) or third-party **API keys** (OpenAI, Anthropic, Google, Azure, OpenRouter, self-hosted). There is no login-based/OAuth path anymore; headless auth is env-var API keys. Under this project's rule (no API keys), that disqualifies it. [source](https://qwenlm.github.io/qwen-code-docs/en/users/configuration/auth/)

**4–6 (for the record).** Approval modes `plan|default|auto-edit|auto|yolo`; docs warn "`--yolo` does not enable a sandbox"; `--sandbox`/`QWEN_SANDBOX` for container isolation. [source](https://qwenlm.github.io/qwen-code-docs/en/users/features/headless/) MCP mirrors Gemini: `mcpServers` in `~/.qwen/settings.json` / project `.qwen/settings.json`, `trust`, `includeTools`/`excludeTools`, `timeout` default 600,000 ms; docs state headless runs respect `trust`/`includeTools`/`excludeTools` "without requiring interactive approval prompts." [source](https://qwenlm.github.io/qwen-code-docs/en/users/features/mcp/) A trusted-folders doc exists (details not pulled — moot given auth). [source](https://qwenlm.github.io/qwen-code-docs/en/users/configuration/trusted-folders/)

**Verdict: disqualified** — API-key-only since 2026-04-15. Ironic, because its headless ergonomics (exit codes, budget flags, buffered JSON) are the best in the Gemini lineage. Re-evaluate only if a login-based auth path returns.

## Kimi (Moonshot) — what actually exists: Kimi Code CLI

**Lineage verified:** the original **kimi-cli** (Python, PyPI `kimi-cli`) carries an official notice: "Kimi CLI is evolving into **Kimi Code CLI** — the next-generation terminal AI agent from the same team… This project will be gradually wound down." The successor is TypeScript, MIT-licensed, at the same GitHub org (repo `MoonshotAI/kimi-cli`, product name Kimi Code CLI; npm `@kimi-ai/kimi-cli`, Node ≥22.19 for npm install, or a standalone install script). Do **not** build against the Python kimi-cli. [source: old repo notice](https://github.com/MoonshotAI/kimi-cli) [source: getting started](https://www.kimi.com/help/kimi-code/cli-getting-started) [source: repo](https://github.com/MoonshotAI/kimi-code) — no claims here about "Kimi K3"; the docs only surface coding model aliases `kimi-for-coding` and `kimi-for-coding-highspeed`; which foundation model those map to is **UNVERIFIED**. [source](https://www.kimi.com/help/kimi-code/membership-guide)

**1. Headless invocation.** `-p, --prompt <prompt>`: "Run a single prompt non-interactively and stream the Assistant output to stdout. This mode does not open the TUI." The prompt is an **argv value; stdin piping is not documented — UNVERIFIED**, so process-list hygiene is an open problem for an adapter. `--prompt` **cannot combine with `--yolo`, `--auto`, or `--plan`** (rejected at startup). [source](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/kimi-command.html)

**2. Structured output.** `--output-format <text|stream-json>`, only valid with `--prompt`, default `text`. No buffered single-JSON mode; the stream-json event schema is **not documented — UNVERIFIED** (an adapter would have to reverse it from output and pin the version). [source](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/kimi-command.html)

**3. Auth.** Two `/login` methods: **"Kimi Code (OAuth)" — device-code flow** ("open the link on any device, sign in, and enter the code") and a Moonshot platform API key. "An active Kimi membership subscription (includes credits) or callable API key is needed." Subscription tiers gate speed ("Allegretto plan or above" for the HighSpeed model). So a subscription-OAuth, no-API-key path **exists** — qualifies. [source: getting started](https://www.kimi.com/help/kimi-code/cli-getting-started) [source: membership](https://www.kimi.com/help/kimi-code/membership-guide)

**4. Read-only enforcement — the big problem.** In `-p` mode, "**no human approval is requested — regular tool calls are handled under the `auto` permission policy**," i.e. headless **auto-approves** tools by default (opposite failure direction from Codex's auto-deny). The read-only `--plan` mode is explicitly incompatible with `-p`. The only documented restriction mechanism is `[[permission.rules]]` in `config.toml` (`pattern` + `decision` `"allow"`/`"deny"`) and per-MCP-server `enabledTools`/`disabledTools`; whether deny rules are honored under the `-p` auto policy is **not documented — UNVERIFIED and load-bearing**: without it there is no enforced read-only headless mode at all. [source: command ref](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/kimi-command.html) [source: MCP/permissions](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/mcp.html) [source: work modes (plan is read-only: "can only use read-only tools… cannot modify any files or run commands")](https://www.kimi.com/help/kimi-code/cli-work-modes)

**5. MCP client.** Solid: `mcp.json` at user level `~/.kimi-code/mcp.json` (or `$KIMI_CODE_HOME/mcp.json`) and project level `.kimi-code/mcp.json`; standard `mcpServers` JSON (`command`, `args`, `env`, `cwd`); per-server `startupTimeoutMs` (default 30,000) and `toolTimeoutMs` (an adapter should raise this, like Frenemy's `tool_timeout_sec = 600`); tools named `mcp__<server>__<tool>`; `enabledTools`/`disabledTools` arrays; "calls that do not match any permission rule trigger an approval request" (interactive). [source](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/mcp.html)

**6. Settings isolation.** None documented — worse, "project-level entry **takes precedence and overrides** the user-level entry" for MCP config, and project `AGENTS.md` feeds the prompt. A cloned repo can inject MCP servers into the run; no `--setting-sources`/trust-gate equivalent found. Doc inconsistency noted: the help center says config lives in `~/.kimi-code/` (`KIMI_CODE_HOME`), while the customization page says `~/.kimi/config.toml` — the docs are in flux; verify on-disk paths at install time. [source: MCP](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/mcp.html) [source: customization](https://www.kimi.com/help/kimi-code/cli-customization) [source: getting started](https://www.kimi.com/help/kimi-code/cli-getting-started)

**7. Timeout/exit.** MCP timeouts configurable (above); CLI exit codes and headless hang history **UNVERIFIED** (product is ~1–2 months old; no meaningful issue-tracker history to mine yet).

**Verdict: viable with serious caveats.** Subscription OAuth ✅, MCP ✅, headless `-p` ✅. Blockers to resolve empirically before building: (a) no enforced read-only in `-p` — must test whether `[[permission.rules]]` deny survives the auto policy; (b) stream-json schema undocumented; (c) prompt-in-argv; (d) project-config injection; (e) very young, docs shifting.

## OpenCode (opencode.ai / sst/opencode) — v1.16.2 local

**1. Headless invocation.** `opencode run [message..]` — "run opencode with a message." **Stdin is read when not a TTY** (`process.stdin.isTTY ? undefined : await Bun.stdin.text()`) and concatenated with the argv message — so stdin-only prompts work. [seen: local `run --help`] [source: run.ts (dev)](https://github.com/sst/opencode/blob/dev/packages/opencode/src/cli/cmd/run.ts) [source: docs](https://opencode.ai/docs/cli/)

**2. Structured output.** `--format json` = **newline-delimited JSON events** (`{type, timestamp, sessionID, …}`): `text` (answer text in `part.text`), `reasoning`, `tool_use`, `step_start`/`step_finish`, `error`. No single-document mode; an adapter must fold `text` events. Exit code 1 on error (`process.exitCode = 1`). [seen: local `run --help` ("raw JSON events")] [source: run.ts](https://github.com/sst/opencode/blob/dev/packages/opencode/src/cli/cmd/run.ts)

**3. Auth.** Subscription/OAuth paths exist: **OpenAI ChatGPT Plus/Pro** (browser OAuth), **GitHub Copilot** (device-code flow), GitLab Duo. **Anthropic Claude Pro/Max** OAuth exists in the flow, but OpenCode's own docs note "Anthropic prohibits using these subscriptions with third-party developer tools" — a ToS landmine, not a technical one; do not build the adapter's happy path on it. OpenCode Zen/Go are API-key products. Credentials in `~/.local/share/opencode/auth.json`. [source](https://opencode.ai/docs/providers/)

**4. Read-only enforcement.** Real and tool-level: `permission` block in opencode.json — `"*"`, `edit` (covers edit/write/patch), `bash`, `webfetch`, `read`, etc., each `allow|ask|deny`; "explicit `deny` rules are still enforced" even under auto-approval. In non-interactive runs (dev source): the `question` permission is force-denied, and any `ask` is **auto-rejected** (`reply: "reject"`) unless auto-approval is on — fail-closed, the right default for a relay. Flag naming discrepancy: local 1.16.2 exposes `--dangerously-skip-permissions` ("auto-approve permissions that are not explicitly denied"); the dev branch source and newer docs call it `--auto` — pin the flag per installed version. Note the docs' permissions page describes `ask` as prompting even under `run`; the source shows non-interactive auto-reject — source wins, but re-verify against the installed version when building. [source: permissions](https://opencode.ai/docs/permissions/) [source: run.ts](https://github.com/sst/opencode/blob/dev/packages/opencode/src/cli/cmd/run.ts) [seen: local `run --help`]

**5. MCP client.** `mcp` block in opencode.json: `"type": "local"`, `command` (array), `environment`, `cwd`, `enabled`, `timeout` (tools-fetch, **default 5000 ms** — raise it for a slow server); remote type with `url`/`headers`/`oauth`. Per-agent/global tool disabling via `tools` glob patterns (`"myserver_*": false`). Per-tool *approval* interaction with the permission system is not fully documented. [source](https://opencode.ai/docs/mcp-servers/)

**6. Settings isolation.** Weak: config merge order is remote → global (`~/.config/opencode/opencode.json`) → `OPENCODE_CONFIG` → **project `opencode.json` → `.opencode` dirs** (project layers override), auto-discovered by walking up to the git root. **No documented way to skip project config**; `--pure` only disables external plugins; `OPENCODE_CONFIG` adds a layer *below* project config rather than replacing it. A cloned repo can therefore inject MCP servers/permissions into the run. [source](https://opencode.ai/docs/config/) [seen: local `--help` for `--pure`]

**7. Timeout/exit.** Long, multi-era history of `opencode run` hang bugs: hangs on API errors ([#8203](https://github.com/anomalyco/opencode/issues/8203)), process never exits after tool calls complete ([#17516](https://github.com/anomalyco/opencode/issues/17516), [#32335](https://github.com/anomalyco/opencode/issues/32335)), hang when the model uses the question tool ([#11899](https://github.com/anomalyco/opencode/issues/11899) — since mitigated by the non-interactive question-deny rule in run.ts), v0.15-era exit hangs ([#3213](https://github.com/anomalyco/opencode/issues/3213)). An adapter must keep Frenemy's hard external SIGKILL timeout; do not trust the process to exit.

**Verdict: viable with caveats.** Enforced deny-based read-only ✅, fail-closed headless ✅, stdin ✅, MCP ✅, subscription OAuth ✅ (via ChatGPT/Copilot — avoid the Claude-sub path on ToS grounds). Caveats: NDJSON-only output, project-config injection risk, documented hang history (external timeout mandatory), CLI flag churn between docs and releases.

### Cross-cutting design notes for a generic adapter layer

1. **Output parsing needs three strategies, not one:** single-JSON-document (Claude, Gemini), NDJSON event streams (Codex, OpenCode, Kimi stream-json), and buffered JSON array (Qwen). The current `JSON.parse(out)` in `ask-claude-mcp.mjs` only covers the first.
2. **Stdin prompts are not universal:** Claude/Codex/Gemini/Qwen/OpenCode take stdin; **Kimi Code is argv-only as documented** — the "prompts never in process lists" guarantee can't be promised uniformly.
3. **Headless approval defaults split into fail-open vs fail-closed:** Codex auto-denies MCP calls (needs per-tool approve), Gemini denies confirmable tools, OpenCode auto-rejects asks — but **Kimi auto-approves** everything in `-p`. The adapter contract "read-only is enforced" is cheap on five CLIs and currently unprovable on Kimi.
4. **Settings isolation is the rarest capability:** only Claude has a real `--setting-sources` switch; Codex gates project config on trust; Gemini's gate is opt-in; Kimi and OpenCode have none. For those, the adapter should launch from a controlled cwd (as the MCP server already does) rather than the cloned repo root, or accept the injection risk explicitly.
